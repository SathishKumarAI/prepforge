**Why a chat system must be built around *eventual consistency and locality***  
A user’s “message” is essentially an immutable event that has to reach every member of a conversation within seconds. The fundamental problem is *low‑latency, high‑throughput replication* across many geographically dispersed data centers while preserving order for each participant.  

1. **Write path** – A message is first stored in a local partition (sharded by chat‑id) and immediately acknowledged to the sender. This guarantees low latency.  
2. **Replication** – The event is asynchronously forwarded to other partitions that own the recipients’ inboxes. Using *vector clocks* or Lamport timestamps lets each node merge replicas without global locks, satisfying causality: a recipient sees messages in the order they were sent.  
3. **Read path** – When a user opens a chat, the client queries its nearest data center for the last N events. Because writes are already replicated, reads can be served from a single node, keeping latency sub‑50 ms.  

The deeper principle is *optimizing for the common case* (local read/write) while tolerating eventual convergence for the rare cross‑region sync.  
**Non‑obvious insight:** Rather than sharding by user ID, shard by *conversation ID*. This keeps all messages of a group together, enabling efficient range scans and reducing cross‑node traffic when a member joins or leaves.
