In a JPA/Hibernate session the **persistence context** is a cache of entity instances that are considered “managed.”  
When you call `session.save(entity)` Hibernate:

1. Generates an identifier (if not already set).
2. Persists a new row immediately.
3. Puts the instance into the context as *new*.

If the entity already has an identifier that matches a row, `save` will **fail** with a duplicate‑key error because it insists on creating a brand‑new record.

`session.saveOrUpdate(entity)` is a safety net:

1. If the object’s identifier is `null` or its state is not yet in the context, Hibernate treats it as *transient* and behaves like `save`.
2. If the identifier exists **and** an entity with that id is already present in the persistence context, Hibernate simply reattaches it (no SQL).
3. If the id exists but no instance is cached, Hibernate issues a `SELECT` to decide whether to perform an `INSERT` or an `UPDATE`.  

Thus `saveOrUpdate` guarantees *idempotent* persistence: “persist this object regardless of whether I already know about it.” It bridges the gap between **optimistic** (assume new) and **pessimistic** (check first) strategies, aligning with the principle of minimal side effects in transaction management.

**Non‑obvious insight:**  
`saveOrUpdate` can *silently* update an entity that was detached but modified elsewhere if its identifier is already present in the context. This means you can reattach a stale object and let Hibernate merge your changes without explicit `merge()` calls, saving code but risking subtle concurrency bugs when two sessions modify the same row concurrently.
