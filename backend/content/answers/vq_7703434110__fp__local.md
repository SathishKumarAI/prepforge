**Why encryption matters for an Azure SQL Database**

The core problem is that a relational database stores *persistent* state: any compromise of the storage medium or network traffic exposes the raw data to attackers. In the cloud this medium is shared among tenants, and the network path is largely outside your control. Therefore you must guarantee confidentiality both at rest (disk) and in transit (client ↔ server).  

**Fundamental solution: Transparent Data Encryption (TDE)**

1. **Encryption key hierarchy**  
   * **Database‑level key** – a symmetric 256‑bit AES key that encrypts the data pages.  
   * **Server‑level key** – a RSA‑2048 key stored in Azure Key Vault, protecting the database key.  

2. **On‑disk transformation**  
   Every write operation first encrypts the page with the database key; reads decrypt it on‑the‑fly. The engine never exposes plaintext to disk I/O layers.

3. **Key management flow**  
   * Create an Azure Key Vault key.  
   * In SQL, create a `CREDENTIAL` that references the vault key.  
   * Use `CREATE DATABASE ENCRYPTION KEY WITH ALGORITHM = AES_256 FROM PROVIDER_KEY = 'vault-key'`.  
   * Enable TDE: `ALTER DATABASE [MyDB] SET ENCRYPTION ON;`

4. **Transport encryption** – always enforce TLS (via Azure portal or `Force Encryption` setting).  

**Non‑obvious insight:**  
TDE protects data at rest, but it does not guard against *database‑level* key compromise. If an attacker obtains the server‑key (e.g., via a compromised Key Vault secret), they can decrypt all databases that use it. Therefore **rotate the server key regularly and store it in a separate vault or HSM**; treat the server key like a root of trust, not just a passive asset.

This layered design satisfies information‑theoretic secrecy at rest, leverages proven cryptographic primitives, and aligns with Azure’s security‑by‑design principles.
