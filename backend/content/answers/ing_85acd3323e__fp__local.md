**Why a CDN matters for a public API + HTML**

A public API is a *stateless* interface that must respond quickly to millions of requests. The raw server can only serve so many calls; every request incurs network latency, TLS handshake, and backend query time. A CDN sits between the client and origin, caching **HTTP responses** in edge nodes distributed worldwide.  

1. **Latency & Bandwidth** – By storing a copy of the API response (or rendered HTML) close to the user, the CDN eliminates round‑trip time to the origin and reduces backbone traffic.  
2. **Consistency via Invalidation** – APIs usually expose immutable or versioned data. The CDN can be instructed to *purge* or *expire* cached objects when the underlying resource changes (e.g., a new API version or updated HTML template).  
3. **Scalable Throughput** – Edge caches absorb spikes; if one origin node fails, traffic can be served from another edge cache without affecting clients.

The deeper principle is **redundant locality**: information that is read more often than it changes should live where the reader lives. A CDN turns every API response into a *read‑heavy* object and distributes replicas accordingly.

> **Non‑obvious insight:**  
> When caching *HTML* generated by an API, treat the HTML as a *composite asset*: its cache key must encode not only the URL but also the set of dynamic data it contains (e.g., user tokens, query parameters). A naive `Cache-Control: public` header can cause *stale or leaking* content if two users share the same cached page. Using a **hash of the serialized response body** as the cache key guarantees isolation while still reusing identical pages across users. This subtle hashing step is often omitted but essential for correctness and security.
