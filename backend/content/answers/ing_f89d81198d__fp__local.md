### Glean Documentation in Machine‑Learning Pipelines

**Fundamental problem**  
ML systems consume *structured artifacts* (datasets, models, hyper‑parameters, evaluation scripts). A pipeline that can automatically discover, index and retrieve these artifacts is essential for reproducibility, debugging, and collaboration. The challenge: each artifact may be stored in a different format or location, and its metadata is often implicit.

**Why the solution must work this way**  
Glean solves it by treating the entire repository as a *graph* of nodes (files, code snippets, training runs) connected by semantic edges (“imports”, “produces”, “depends on”). By crawling the graph once and storing a lightweight index, any query—“Which model was trained on dataset X?” or “Show all experiments that used hyper‑parameter Y”—becomes a simple path‑finding operation. This architecture scales because:

1. **Incremental updates** – only changed nodes are re‑indexed.
2. **Decoupled storage and search** – the graph can live in a NoSQL store, while a search engine (e.g., ElasticSearch) provides fast lookups.

**Connection to deeper principles**  
- *Information theory*: Glean compresses provenance by encoding edges instead of duplicating metadata, reducing redundancy.
- *Graph theory*: Path queries correspond to reachability problems solvable in near‑linear time with adjacency lists.
- *Probabilistic inference*: When a query is ambiguous (e.g., multiple models share the same name), Glean can rank results using Bayesian priors derived from usage frequency.

**Non‑obvious insight**  
Most people treat documentation as static prose. In ML, *documentation is dynamic graph data*. By formalizing it as such, Glean turns the “glue” of a pipeline into first‑class citizens that can be queried, visualized, and even auto‑generated by downstream tools—turning documentation from an afterthought into a core optimization objective.
