**Why “cursor” questions surprise candidates**

At its core, a *cursor* is nothing more than an iterator that points to one element in a data set and can be advanced or rewound.  
The fundamental problem it solves is *sequential access with minimal state*: you need to traverse millions of rows without materialising the whole result set in memory.  

In relational engines this leads to two constraints:

1. **Deterministic progress** – advancing must be O(1) and repeatable, otherwise a query planner cannot estimate cost.
2. **State isolation** – each cursor instance must see a consistent snapshot of the table, even if concurrent updates occur.

These requirements push us toward *index‑based navigation* (B‑trees or hash tables). A cursor’s “current row” is effectively an index key; moving forward means finding the next key in order. The engine can then use page pointers to fetch only the necessary pages, keeping memory usage bounded.

**Non‑obvious insight:**  
Many interviewers ask for cursor implementation details expecting a naive linked‑list walk. The real twist is that **cursors are often *lazy* and *materialised on demand***: the engine keeps only the key of the current row; all data is fetched when `FETCH NEXT` is called. This laziness allows cursors to support *scrollable*, *updatable*, and even *dynamic* result sets without a full materialisation, which would otherwise violate the O(1) advance requirement.

Understanding this lazy‑key mechanism reveals why cursor code must be highly optimised around index traversal, not just simple row copying.
