### Why compaction must delete old SSTables

A key‑value store writes data first to a log (commit‑log) and then flushes it into immutable *SSTables* on disk.  
Each write creates a new, larger file; reads walk the newest files first, but over time the number of files explodes, degrading I/O locality, increasing read amplification, and consuming storage.  
The only way to keep the system tractable is to **merge** (compact) several SSTables into one, discarding obsolete or overwritten keys.  This is an *online* form of lossless data compression: every key/value pair that survives the merge must be present in exactly one output file; all others are dropped because they have been superseded by newer timestamps.

### The underlying optimisation

The compaction problem can be cast as a **set‑cover** with costs:  
- *Cost* = I/O to read input files + write new output.  
- *Constraint* = All keys that remain after the merge must appear in the output.  

We want to minimise the total cost while keeping the number of live SSTables below a target.  This is NP‑hard, so ScyllaDB uses greedy heuristics that approximate the optimum.

### Compaction strategies

| Strategy | Greedy heuristic | When it shines |
|----------|------------------|---------------|
| **Size‑Tiered** | Merge files whose total size ≈ target tier (e.g. 4 MiB). | Workloads with many small writes; keeps read amplification low. |
| **Leveled** | Maintain leveled hierarchy: each level L has at most *k* times the size of L‑1 and no overlapping key ranges. | Heavy reads, predictable latency. |
| **Time‑Window** | Merge files written within a sliding window (e.g., 10 min). | Time‑series workloads where recent data is queried more often. |

Each strategy balances **read amplification** (how many SSTables must be read for a key) against **write amplification** (how much extra I/O compaction incurs).

### Non‑obvious insight

Most people think compaction simply “keeps the number of files down.”  In fact, *the shape* of the file size distribution matters more: a perfectly leveled hierarchy guarantees at most one read per key per level, whereas a poorly sized tiered merge can cause many small reads to hit dozens of SSTables.  
By modelling compaction as a set‑cover problem and using greedy approximations that respect *key‑range* locality, ScyllaDB achieves both storage efficiency **and** bounded read latency—an elegant marriage of combinatorial optimisation and practical system design.
