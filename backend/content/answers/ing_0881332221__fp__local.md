**Idempotency for In‑Progress Requests: A First‑Principles View**

The core problem is *state‑inconsistency* caused by network unreliability: a client may resend a request (e.g., “add this feature vector to the model”) while the original is still being processed. If each retry triggers a new update, the system diverges from its intended state, violating **linearizability** for the client’s perspective.

From an *optimization* standpoint, we want the final objective function to be evaluated once per logical operation. Treating each retry as a separate gradient step would bias the model toward duplicate data and inflate training time—an unnecessary computational cost with no benefit.

The solution is to make every request **idempotent**: the effect of applying it multiple times equals applying it once. Mathematically, let `f(x)` be the update operator for an input `x`. We require  
`f(f(x)) = f(x)`. This property follows from defining a deterministic *operation key* (e.g., a UUID or hash of payload + timestamp). The server stores a set `S` of keys that have been applied; upon receiving a request, it checks `k ∈ S`; if so, it simply returns the cached result instead of recomputing. Thus, the system behaves as a *monoid* over operations: combining duplicate requests yields the same monoid element.

**Non‑obvious insight:**  
Idempotency is not just about preventing double work; it also guarantees **commutative safety** for concurrent updates. If two in‑progress requests share an operation key, they are effectively the same logical update, so their execution order no longer matters—this turns a potentially non‑commutative training pipeline into one that behaves like a commutative monoid, simplifying consistency guarantees across shards and replicas.

In short, idempotency turns unreliable retries into deterministic state transitions, preserving both correctness and efficiency in machine‑learning systems.
