**Why agents need a tool‑use framework**

At its core, an intelligent agent is an optimizer of *utility* over time: it observes the world, selects actions, and updates beliefs to maximize future reward.  
When the action space is continuous (e.g., robot arm movements) or combinatorial (e.g., writing code), the raw policy network cannot explore all possibilities; its capacity is finite. A **tool**—a pre‑trained model or API with a well‑defined interface—provides a *structured hypothesis space* that captures domain knowledge far beyond what the agent could learn from scratch.

Formally, let \(A\) be the set of primitive actions and \(T=\{t_1,\dots,t_k\}\) the set of tools. Each tool \(t_i\) implements a function \(f_i: \mathcal{S}\times\mathcal{O}\to \mathcal{S}\) (state → state) conditioned on an *objective* \(\mathcal{O}\). The agent’s policy \(\pi(a|s)\) is augmented to output sequences of tool calls and primitive actions. This turns the optimization problem into a *hierarchical MDP*: high‑level decisions choose which subproblem to delegate, while low‑level controllers handle execution.

**Deeper principle: modularity as inductive bias**

Modularity reduces sample complexity by reusing learned components across tasks. In information‑theoretic terms, each tool compresses the policy’s representation of a subtask into a concise “semantic vector” (e.g., the output of GPT). The agent only needs to learn *how* to compose these vectors, not how to generate them from scratch.

**Non‑obvious insight**

Many designs treat tools as black boxes. The subtlety is that **the interface itself must be learned**: the agent must discover *which part of a tool’s output is useful for its own state transition*. This meta‑learning problem—“learning to call the right part of a tool”—is often overlooked, yet it governs whether an agent can truly leverage external knowledge or merely regurgitates it.
