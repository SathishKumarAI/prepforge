**Event‑Sourcing: the “why” behind its necessity**

At its core an application must *record* every change that matters to its state.  
In a conventional system you mutate in‑memory objects and persist snapshots; if a bug occurs you have no trace of why the object arrived at its current value.  
Event‑sourcing replaces the mutation with a *sequence of immutable events*: “OrderPlaced”, “ItemAdded”, “PaymentReceived”.  

Why does this work? Because an event is a **minimal, self‑contained observation** that can be replayed deterministically. By treating the event stream as the single source of truth we:

1. **Guarantee auditability** – every state change is a log entry, so reconstruction and debugging become trivial.
2. **Enable temporal queries** – you can ask “what was the cart at 14:03?” by replaying up to that timestamp.
3. **Facilitate eventual consistency** – distributed systems can publish events locally; other services subscribe and update their projections asynchronously.

The deeper principle is *functional purity*: a pure function from past events to current state means no hidden side‑effects, thus easier reasoning about concurrency and failure recovery.

**Non‑obvious insight:**  
Many adopt event‑sourcing only for auditability, overlooking its role as an *explicit contract* between producers and consumers. Each event type defines the API of a bounded context; any change to that contract requires versioning or migration. Treating events as contracts turns the system into a living schema registry, ensuring backward compatibility without extra tooling.
