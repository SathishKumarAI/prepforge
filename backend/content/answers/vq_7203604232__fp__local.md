Finding a particular file name in HDFS is essentially a *metadata* query rather than a data‑scan problem.  
The fundamental issue is that HDFS stores **file blocks** on DataNodes, but the only place where names and paths live is the **NameNode’s namespace tree** (a persistent trie). Therefore any “search for *foo.txt*” must be answered by walking that in‑memory structure, not by reading block data.  

The simplest command leverages this:  

```bash
hdfs dfs -ls / -R | grep 'foo\.txt$'
```

`-R` makes the DFS client request a recursive listing from the NameNode; the client streams back directory entries (path, permissions, size) and `grep` filters them locally. Because the list is generated by the NameNode, it runs in **O(number of‑files)** time, independent of block placement or network I/O.  

A more powerful approach uses the Hadoop FileSystem API’s *glob* support:

```bash
hdfs dfs -ls /path/part-* | grep 'foo\.txt$'
```

The NameNode can resolve `*` on a single directory without recursing into sub‑directories, which saves RPC round‑trips.  

**Non‑obvious insight:**  
If you need to search *content* for a string (not just the name), HDFS cannot do this efficiently because it lacks full‑text indexes. The common pattern is to run a lightweight MapReduce job that emits `(fileName, line)` pairs and filters on the reducer. This turns an I/O‑bound problem into a distributed filter that scales with cluster size—an example of turning *information* into *computation* by exploiting HDFS’s data locality.
