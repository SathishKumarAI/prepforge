### Why an LOV needs a source at all

A List‑of‑Values (LOV) is a UI construct that lets the user pick from a finite set of permissible entries.  
From an information‑theoretic view, it is a *constraint* on the domain of a form field: instead of letting the user type any string, we restrict the choice to a known subset. The implementation must therefore supply that subset somewhere—either pre‑fetched into memory or generated on demand.

### Record groups vs. direct queries

The most common way in Oracle Forms is to create a **record group** (a reusable set of rows) and bind it to the LOV.  
But a record group is just an *in‑memory table*; the underlying data still comes from a query.  
You can skip the record‑group layer entirely by defining the LOV with a **SELECT statement** directly:

```sql
LOV_NAME = 'CUSTOMER_LIST'
QUERY    = SELECT cust_id, cust_name FROM customers WHERE active = 'Y';
```

The form engine will execute that query each time the LOV is opened (or use caching flags).  
Thus, the record group is an optimization/abstraction layer, not a requirement.

### Non‑obvious insight

Because the query can contain bind variables, you can make the LOV *contextual* without any record‑group persistence. For example:

```sql
SELECT order_id, status FROM orders WHERE cust_id = :P_CUST_ID;
```

When the user opens the LOV for an order field, the current customer ID automatically filters the list—no need to maintain a separate record group that would otherwise have to be refreshed every time `:P_CUST_ID` changes. This dynamic binding is often overlooked but can simplify code and reduce memory usage dramatically.

**Bottom line:** An LOV does not *require* a record group; it only needs a source of rows, which can be supplied directly by a query.
