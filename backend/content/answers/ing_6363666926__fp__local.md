**Why we need a short URL?**  
When the world moves online, *links* become the currency of information exchange. A typical URL can be 200 characters long; sharing it via SMS, print, or limited‑width interfaces is cumbersome. The problem reduces to **compressing a unique identifier while guaranteeing collision‑free retrieval and high throughput**.

### Fundamental building blocks

1. **Key generation** – We need a bijection from *n* possible URLs to a compact space (e.g., 6–8 base‑62 characters).  
   - *Why hashing alone fails*: cryptographic hashes are large; they expose the input size and can collide under attack.  
   - *Solution*: Use a **monotonic counter** (or Snowflake‑style ID) and encode it in base‑62. This guarantees uniqueness, preserves insertion order (useful for analytics), and keeps IDs short.

2. **Storage & lookup** – A single table with columns `(id, long_url)` is sufficient.  
   - *Why not a key–value store?* Because the `id` itself is the key; we avoid expensive joins or secondary indices.  
   - *What about scaling?* Replicate the hash table across shards keyed by the first few bits of the ID; this gives O(1) lookups with linear scalability.

3. **Redirection logic** – The service receives a request for `/abc123`. It decodes `abc123` → integer, probes the shard, and returns an HTTP 301 to the stored URL.  
   - *Why 301?* Search engines preserve link equity; clients are redirected without extra round‑trips.

### Non‑obvious insight

**The counter itself is a source of entropy that eliminates the need for random collision checks.** Many designs rely on random IDs and then retry on collision, which introduces latency spikes under load. By making the ID generation *deterministic* (monotonic), we guarantee O(1) creation time regardless of traffic volume.

### Summary

A URL shortener is essentially a **compact bijective mapping + distributed lookup**. The counter‑based approach aligns with information theory: we pack 6 bits per base‑62 character, approaching the theoretical minimum for unique IDs while keeping the system simple and highly performant.
