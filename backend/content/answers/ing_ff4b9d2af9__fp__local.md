**Why idempotent APIs matter**

In any distributed system the *only* reliable observable is the set of messages that reach it.  
A client may retry a request because a network glitch or an out‑of‑band timeout occurred, but the server must guarantee that reprocessing the same message does not alter global state in an unintended way.  

Formally, let \(f\) be the operation invoked by a request and \(S\) the system state.  
We require

\[
\forall s \in S,\;\; f(f(s)) = f(s).
\]

This is the *idempotence* law. It turns an arbitrary sequence of retries into a deterministic function, which in turn makes reasoning about failures a simple matter of applying a fixed‑point equation.  

**Design principle**

Treat each API endpoint as a pure functional transformation on a *snapshot* of state rather than a mutable procedure.  
1. **Versioned resources**: expose a stable URI that always represents the same entity, regardless of how many times it is touched.  
2. **Explicit idempotency keys**: let clients supply an identifier; the server records the result of the first invocation and returns that on subsequent calls with the same key.  
3. **Side‑effect isolation**: separate “write” actions (POST/PUT) from “read” actions (GET), ensuring reads are naturally idempotent.

**Non‑obvious insight**

Most developers think idempotency is only about *retries*.  In reality, it also protects against *duplicate payloads* that may be generated by client bugs or network intermediaries. By making the server stateful with respect to an idempotency key, you convert a potential non‑deterministic side effect into a deterministic lookup, thereby eliminating a whole class of race conditions and simplifying cacheability.

In short: design every endpoint as a pure function of its input plus a stable resource identifier; guard that function with an idempotency key so retries become harmless lookups.
