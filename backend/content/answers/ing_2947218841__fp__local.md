**Why a CDN is essential in ML‑driven systems**

At the core, an ML service must serve inference results (model weights, predictions) to many clients with *low latency* and *high reliability*.  
A CDN solves this by turning the *information‑propagation problem* into a **geometric covering problem**: place caches at nodes that minimize the expected travel distance for requests. By replicating model artifacts near users, the network turns a global, costly “single‑origin” communication into many local, low‑bandwidth exchanges.  

**Key benefits derived from this geometry**

| Benefit | Principle | Reasoning |
|---------|-----------|----------|
| **Latency reduction** | Shortest‑path routing in a sparse graph | Cached copies eliminate the long hop to origin; the path length shrinks proportionally to the distance between user and nearest cache. |
| **Bandwidth savings** | Load balancing + traffic aggregation | Popular models are hot spots; caching turns repeated requests into local hits, freeing backbone capacity for other traffic. |
| **Fault tolerance** | Redundancy in distributed systems | If one edge server fails, others can serve the same content; the system’s availability is governed by the *coverage* of the cache network. |
| **Scalability** | Distributed caching scales sub‑linearly with user base | Adding a new edge node increases capacity without overloading any single origin; the overall service cost grows only logarithmically. |

**Non‑obvious insight:**  
Because ML models often evolve slowly, a CDN’s *stale‑content tolerance* turns into an optimization: you can cache older model versions for long‑tail users while pushing updates to hot spots, thereby trading freshness against bandwidth. This subtle “soft consistency” is rarely exploited but yields huge cost reductions in production ML pipelines.
