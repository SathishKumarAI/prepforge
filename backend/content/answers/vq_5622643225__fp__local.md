**Why a “time‑difference” query is fundamentally an *optimization* problem**

When you ask for the difference between two timestamps, you’re really asking: *“What minimal set of operations can transform one temporal value into another?”*  
In relational terms this boils down to evaluating a **scalar function** on each row and then aggregating or ordering by that result. The engine must therefore:

1. Parse the two columns as *temporal types* (not strings).  
2. Compute the numeric distance in a unit of choice (seconds, minutes, days…).  
3. Return the value without altering the underlying data.

Because every row is independent, this is a **pure function** – no state is carried across rows. The optimizer can therefore push the calculation down to storage (e.g., using index‑only scans if the column is indexed) and avoid materializing intermediate results.

---

### Typical SQL formulation

```sql
SELECT 
    id,
    start_ts, 
    end_ts,
    EXTRACT(EPOCH FROM (end_ts - start_ts)) AS diff_seconds   -- PostgreSQL
FROM   events;
```

- `start_ts` & `end_ts` must be of a timestamp type.  
- Subtracting yields an **interval**; `EXTRACT(EPOCH)` converts it to seconds.  

In MySQL you would use `TIMESTAMPDIFF(SECOND, start_ts, end_ts)`.  
If you need days or hours, change the unit accordingly.

---

### Non‑obvious insight

Most people treat the subtraction as a “pure arithmetic” step, but **intervals in SQL are *not* always comparable across time zones**. If either column is `TIMESTAMP WITH TIME ZONE`, the database normalizes to UTC before subtraction. Thus two rows that look identical in their local times may produce different differences if stored in different zones. Always be explicit about time zone handling or cast to a common zone first.
