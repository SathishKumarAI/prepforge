**Snapshots in HDFS – a principled view**

At its core HDFS must provide *immutable*, point‑in‑time views of distributed files for backup, rollbacks and versioning.  
A snapshot is a logical *copy* of the namespace that takes constant time regardless of file size: it only records the inode tree at the moment of capture. The underlying blocks stay unchanged; new writes are appended as usual, while old block pointers survive in the snapshot metadata.

Why this design?  
1. **Space efficiency** – a snapshot is essentially a reference‑counted view; no data duplication until a write occurs (copy‑on‑write).  
2. **Atomicity & consistency** – by recording the entire namespace tree atomically, all clients see either the pre‑snapshot or post‑snapshot state, never an intermediate mix.  
3. **Performance isolation** – read traffic to snapshots can be served from the same blocks as live data without locking writers.

The deeper principle is *lazy persistence* in distributed storage: only materialize changes when necessary, keeping I/O bounded.  

A non‑obvious insight: because snapshots are namespace‑level, they expose the *hierarchical* nature of HDFS to clients. This allows incremental backup tools to traverse only changed directories, drastically reducing network load—something that flat file systems cannot offer without extra metadata.
