**Scaling a Client‑Server Architecture for Machine Learning**

The core problem is *how to keep latency low while ingesting many model requests* without duplicating expensive inference resources.  
1. **Workload decomposition** – split the monolithic “client → single server” into micro‑services: (a) an API gateway, (b) a request queue, and (c) multiple stateless inference workers.  
2. **Load balancing & elasticity** – treat each worker as an *identical stateless service*; a scheduler distributes requests by round‑robin or least‑congested‑queue, enabling horizontal scaling with linear throughput.  
3. **Consistency & freshness** – model updates are propagated via *immutable checkpoints*. Workers pull the latest checkpoint only on restart, guaranteeing that all in‑flight requests see the same version while avoiding locks.  
4. **Caching & sharding** – cache frequent inference results (e.g., embeddings) at edge nodes; shard data stores by feature space to reduce contention.

The deeper principle is *optimizing information flow under resource constraints*: we trade off consistency for availability, a concrete instantiation of the CAP theorem tailored to ML latency budgets.  

**Non‑obvious insight:** By treating inference as an *event stream* (each request → event) and processing it asynchronously, you decouple compute from response time. The client sees a quick “queued” reply; the worker processes at its own pace, allowing burst handling without overprovisioning GPUs or CPUs. This asynchronous pipeline is often overlooked but dramatically improves both cost efficiency and user experience.
