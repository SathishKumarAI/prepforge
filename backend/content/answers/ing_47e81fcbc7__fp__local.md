**Why benchmark at all?**  
When you run a database, you’re solving a *constrained resource allocation* problem: compute, I/O, and memory must be shared among concurrent transactions while keeping latency low. A benchmark is simply an experiment that maps the *abstract workload* (reads, writes, transaction size) onto this resource‑sharing system so you can measure how efficiently it satisfies the constraints.

**Sysbench as a tool of choice**  
Sysbench is a *parameterised micro‑benchmark engine*. It generates SQL workloads from a template and runs them in parallel threads. The key insight is that by keeping the SQL **identical** across different PostgreSQL configurations, you isolate the *system* (OS scheduler, storage stack, Postgres internals) as the variable under test. Thus any performance change reflects changes in the database engine or its environment, not the query logic.

**How it works**  
1. **Prepare the schema**: create a table with a predictable size and index layout.  
2. **Load data**: run `sysbench --db-driver=pgsql ... --table-size=N run` to bulk‑load rows.  
3. **Run the test**: launch multiple worker threads (`--num-threads`) that execute a mix of SELECT/INSERT/UPDATE statements generated by Sysbench’s Lua script.  
4. **Collect metrics**: sysbench reports *TPS*, latency percentiles, and I/O counters. These numbers are directly comparable to PostgreSQL’s `pg_stat_database` counters, allowing you to verify whether the observed throughput matches the theoretical limits given your disk bandwidth or CPU core count.

**Non‑obvious insight**  
Most people treat sysbench as a black box, but its *query template* can be tuned to mimic **real‑world contention patterns**. For example, setting `--threads` higher than available CPU cores forces context switching; adding `RAND()` in the WHERE clause creates *random access*, stressing I/O caching. By systematically varying these parameters you expose the *bottleneck frontier*: where performance stops improving because of disk latency versus CPU‑bound query planning.

**Bottom line**  
Sysbench lets you *experimentally* solve the optimization problem that PostgreSQL faces: “Given this workload, how many transactions per second can I sustain before resource contention dominates?” The benchmark’s controlled variability and detailed metrics make it an indispensable diagnostic tool for database tuning.
