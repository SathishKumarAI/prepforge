**Why debugging a CDN is inherently hard**

A CDN distributes content across *N* edge nodes so that any user request hits the nearest replica. The system solves a **low‑latency routing problem**: for each request, pick the node with minimal network cost while respecting cache hit rates and capacity constraints. This optimisation is *online*—requests arrive unpredictably—and *distributed*, meaning no single component sees the full state.

Because of this:

1. **State locality** – metrics (cache miss ratio, RTT) are spread across edge nodes; a fault in one node looks like a global degradation until you locate it.
2. **Transient network partitions** – a routing change can temporarily redirect traffic to suboptimal nodes, causing a cascade that disappears once the topology stabilises.
3. **Stale data propagation** – cache invalidation messages are eventually consistent; by the time you realise a stale object is being served, many users have already consumed it.

These properties map to the *no‑free‑lunch theorem* in distributed optimisation: any improvement (e.g., faster routing) inevitably introduces new failure modes. The deeper insight is that **debugging complexity is proportional to the number of independent optimisation variables**—the more nodes and metrics you optimise over, the harder it becomes to isolate a single culprit.

A practical antidote is *observable decomposition*: instrument each edge node with a lightweight “health beacon” that aggregates only local anomalies. Feed these beacons into a central anomaly‑detection engine that reconstructs the global state from partial views, dramatically reducing search space and turning an NP‑hard localisation problem into a tractable one.
