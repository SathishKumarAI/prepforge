**Why “event‑driven” is essential to Event Sourcing**

At its core, a system must *record* every change that matters.  
Event‑Sourcing does this by persisting an immutable log of **events**—the
atomic facts that caused state transitions (e.g., `OrderPlaced`, `ItemShipped`).  
The *driven* part comes from the fact that *everything else in the system is a reaction to those events*, not to arbitrary method calls or database queries.

1. **Fundamental problem** – In distributed, long‑lived systems you need a single source of truth that guarantees consistency, auditability, and replayability.  
2. **Why it must be event‑driven** – If downstream components (read models, microservices, analytics) act on *commands* or *queries*, they risk falling out of sync with the canonical state; race conditions arise when multiple commands mutate the same entity concurrently. By reacting to a stream of events, each consumer processes changes in the exact order they occurred, preserving causality without locking.  
3. **Connection to deeper principles** – The event stream embodies *causal sufficiency*: the minimal set of observable facts that fully determines future states. This aligns with information‑theoretic notions of entropy reduction—once an event is recorded, it reduces uncertainty about the system’s history.

### Non‑obvious insight  
An event is not merely a log entry; it also functions as a *declarative contract*. Because events are immutable and typed, consumers can evolve independently: adding new projections or services without touching existing code. This decoupling turns the event stream into a publish‑subscribe bus that automatically provides eventual consistency for free.

In short, “event‑driven” means every state change is first written as an event, and all subsequent behavior—read models, side effects, notifications—is triggered by consuming those events in order. It guarantees correctness, auditability, and extensibility in a single, elegant design.
