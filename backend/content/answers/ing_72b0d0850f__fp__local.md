### Evaluating an Indic LLM from First Principles  

**Fundamental problem:**  
An LLM must *model the statistical regularities of a language* so that it can generate coherent text and answer queries in that language. The evaluation metric is therefore the *expected log‑likelihood* (or equivalently perplexity) on held‑out data drawn from the same distribution as user inputs.

**Why translation breaks this:**  
1. **Distribution shift** – Translated English corpora are generated by a *different process* than native Indic text. They carry artefacts of the source language’s syntax, idioms, and lexical choice, which skew the target‑language model away from its true distribution.  
2. **Information loss** – A one‑to‑one translation can drop or alter culturally specific references (e.g., proverbs, regional dialects). The resulting test set no longer probes the model’s ability to handle those nuances.  
3. **Unbalanced coverage** – Translators often default to standard Hindi or Bengali forms that underrepresent local registers, thereby biasing the evaluation toward a narrower slice of the language space.

**Proper evaluation pipeline**

| Step | Rationale |
|------|-----------|
| 1️⃣ **Native‑speaker curated corpora** (web text, literature, social media) | Reflects true usage distribution. |
| 2️⃣ **Token‑level cross‑entropy** on a held‑out split | Directly measures log‑likelihood; no translation artefacts. |
| 3️⃣ **Task‑specific benchmarks** (QA, summarization) with *native* prompts and answers | Tests higher‑order reasoning in the target language. |
| 4️⃣ **Human‑in‑the‑loop sanity checks** for cultural relevance | Ensures model respects idiomatic nuance. |

**Non‑obvious insight:**  
Even a perfect perplexity score does not guarantee *semantic fidelity*. A model can achieve low perplexity by memorizing high‑frequency collocations but fail to resolve ambiguous pronouns or contextual sarcasm. Thus, evaluation must combine **distributional metrics** with **contextual comprehension tests** that expose the model’s internal representations beyond surface token frequencies.

In short, an Indic LLM should be judged on *native data* and *meaningful tasks*, not on translated proxies—only then does the metric truly reflect its capability to serve speakers of that language.
