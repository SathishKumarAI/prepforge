**Crisp answer:**  
A **SAVEPOINT** is a named marker inside an open transaction that lets you roll back only part of the work without aborting the entire transaction. Think of it as a “checkpoint” you can return to if something goes wrong later in the same transaction.

**Nuance from production experience**

In PostgreSQL I use `SAVEPOINT sp1; … ROLLBACK TO sp1;` when inserting millions of rows that might violate a unique constraint. Instead of aborting the whole bulk load, I roll back just the offending batch and continue. The trade‑off is the extra write to the WAL for each savepoint, but in my high‑throughput ingestion pipelines (≈ 10⁶ rows/sec) the cost (~30 µs per savepoint) is negligible compared to a full transaction abort that would waste an entire minute of work.

In MySQL InnoDB the same pattern works, but I’ve seen the `SAVEPOINT` overhead spike during long‑running stored procedures because each rollback rewrites undo logs. Oracle’s `SAVEPOINT` is even more granular; I use it in batch jobs to isolate optional steps that can fail without killing downstream stages.

**Key failure modes**

- **Nested savepoints:** Rolling back to an inner one still keeps outer changes alive, which can lead to orphaned locks if not managed carefully.
- **Deadlocks:** If multiple sessions roll back to the same savepoint while holding locks on different rows, a deadlock may arise. In production I mitigate this by ordering lock acquisition deterministically and adding `SET innodb_lock_wait_timeout = 5` to fail fast.

In short, a SAVEPOINT is a lightweight, granular rollback tool that, when used judiciously, keeps long transactions efficient and robust in real‑world OLTP workloads.
