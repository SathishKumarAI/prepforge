### Why Elasticsearch sorts Geo‑Points the way it does

When you store a location as `[lon, lat]` and ask for *sorted* search results, Elasticsearch must answer two questions:

1. **What is “closest”?**  
   The distance between two points on Earth is a function of their spherical coordinates. A naïve Euclidean distance in Cartesian space would give wrong rankings near the poles or across the 180° meridian.

2. **How to rank many documents efficiently?**  
   Sorting by an arbitrary function over millions of rows requires pre‑computed indices, otherwise each query would recompute distances on the fly.

Elasticsearch resolves this by:

- Converting every `[lon, lat]` pair into a *geohash* (a hierarchical spatial prefix) and storing it in a dedicated **geo_point** field.  
- Building an inverted index of these geohashes so that a query can quickly locate all documents whose geohash prefixes fall within the requested radius.  
- Using the Haversine formula (or a planar approximation for small distances) to compute the exact distance only for the candidate set, then applying **`sort: { "_geo_distance": {...} }`**.

The deeper principle is *information locality*: by organizing points into a spatial hierarchy we reduce the search space logarithmically. The non‑obvious insight?  
Sorting on `_geo_distance` does **not** sort documents by their raw coordinates; it sorts by *distance to the query point*. This distinction matters because two points with identical longitudes can still rank differently if their latitudes differ, and vice versa. Understanding this subtlety prevents misinterpreting “sorted by latitude” as a valid geo‑sort.
