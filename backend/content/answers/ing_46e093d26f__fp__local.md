**Why an “offline‑delivery” layer is inevitable**

When a user goes offline the network graph is cut: every outgoing edge (a connection to another device) disappears. The *only* way to guarantee eventual consistency of messages is to buffer them somewhere that remains reachable by the server, regardless of which user’s device is up next. This buffering must be **state‑ful** (to remember who has received what), **partition‑tolerant** (so it survives a node failure), and **low‑latency** for the client.

**Design principle – “store‑once, deliver‑anytime”**

1. **Message queue per conversation**  
   * Each conversation gets an append‑only log on a replicated store (e.g., Kafka + RocksDB).  
   * Append is idempotent: duplicates are harmless because the client acknowledges by ID.

2. **Per‑user delivery cursor**  
   * The server keeps, for every user, a monotonically increasing offset per conversation.  
   * When the user reconnects, the server streams all log entries whose offset > cursor.  

3. **Back‑pressure & compaction**  
   * After a message is acknowledged by all current participants, it can be compacted (deleted) to free space.  
   * A background job runs a “garbage‑collect” sweep that respects read receipts.

4. **Edge case: new device joins**  
   * The new device receives the conversation log from the last known cursor of its user ID; if none exists, it starts at zero.

**Non‑obvious insight**

The *cursor* is not a simple counter—it must be **consistent across replicas**. If one replica lags and delivers an older message before a newer one, the client may see out‑of‑order deliveries. By using vector clocks per conversation (or a globally monotonic “delivery ID” generated by a single sequencer), we guarantee that all replicas deliver messages in the same total order without extra network round‑trips.

This architecture turns the offline problem into a deterministic stream‑consumption task, leveraging proven queueing theory while keeping latency low for real‑time chats.
