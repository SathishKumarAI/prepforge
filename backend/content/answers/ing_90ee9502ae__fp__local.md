### Why you need to embed an OpenSearch dashboard

When a product team builds a BI‑centric feature (e.g., a real‑time analytics pane in a SaaS app), they want **interactive visualisations that reflect the same data lake** used by their internal dashboards. Pulling the raw dataset into the app and re‑plotting it is costly, fragile, and hard to keep consistent.  
OpenSearch Dashboards already provide a full‑featured, real‑time charting engine backed by the exact index you query in your application. The problem becomes: *how do we expose that UI inside our own web pages without compromising security or user experience?*

### What the solution must guarantee

1. **Isolation** – The embedded dashboard should run in its own sandbox so it can use its own CSS/JS and not clash with the host page.  
2. **Authentication** – Users of your app shouldn’t have to log into OpenSearch separately; the request must carry the same IAM or Cognito identity that authenticated them.  
3. **Performance** – The embedding layer should be lightweight, adding minimal latency.

These constraints naturally lead to a *signed‑URL + iframe* pattern: generate a short‑lived URL that authorises the dashboard view, then embed it in an `<iframe>` whose origin is controlled by your application’s domain.

### Deep principle: **Security through delegation**

OpenSearch’s signed URLs are essentially *delegated credentials*. They encode a cryptographic hash of request parameters and a TTL. When the iframe loads, OpenSearch verifies the signature, ensuring that only requests generated by your trusted backend can render the dashboard. This is the same mechanism used for pre‑signed S3 objects: you delegate read/write access without exposing long‑term keys.

### One non‑obvious insight

Most tutorials stop at “put an `<iframe>`.” The trick that often breaks production deployments is **CORS and CSP**. OpenSearch Dashboards set a strict `X-Frame-Options` header (`SAMEORIGIN`). To allow embedding, you must either:

* run OpenSearch behind a reverse proxy that rewrites the header, or  
* use AWS’s *OpenSearch Service domain policy* to add an `X-Frame-Options: ALLOW-FROM <your‑app>` rule.

Neglecting this step results in silent “blocked from loading” errors that are hard to debug. Handling it early keeps your integration robust and secure.
