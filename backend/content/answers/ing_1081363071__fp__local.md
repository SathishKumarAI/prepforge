**Why indexes are indispensable**

At the heart of a database is the *lookup problem*: given a key (e.g., `user_id = 42`), find all rows that satisfy it. A naïve scan examines every row; its cost grows linearly with table size \(O(n)\). An index transforms this into a search on an auxiliary structure whose depth depends on the number of entries, not the entire table.

1. **Logarithmic time** – Most indexes (B‑trees, B+ trees) are balanced, guaranteeing \(O(\log n)\) lookups. This is the only way to keep query latency constant as data scales.
2. **Range queries** – Because keys are stored in sorted order, contiguous ranges (`BETWEEN 100 AND 200`) can be served by a single traversal of leaf nodes, avoiding repeated random I/O.
3. **Predicate push‑down** – The database engine can use the index to filter rows *before* reading them into memory, reducing disk traffic and CPU usage.
4. **Covering indexes** – If all columns required for a query are present in the index, no base table access is needed at all.

A non‑obvious insight: *indexes trade space for entropy*. By storing a compressed, sorted representation of keys, they reduce the effective information content that must be examined. The deeper principle is **information theory**—an index partitions data into buckets, each bucket representing a low‑entropy subset; querying simply selects the relevant bucket, dramatically lowering uncertainty.

In short, indexes are the only practical means to turn a linear scan into a logarithmic search, enabling scalable, high‑throughput database systems.
