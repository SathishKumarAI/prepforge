**High‑Level Architecture – “Eureka” (Netflix’s Service Discovery)**  

The core problem: *how do stateless microservices find one another without hard‑coded endpoints, while tolerating dynamic scaling and failures?*  
A naïve solution would be to ship configuration files or environment variables with each deployment. That approach breaks when services scale up/down or are replaced; clients would need a redeploy for every change—an optimization nightmare.

Eureka solves this by turning discovery into an *information‑theoretic exchange*: each service registers its own URI and health status, then periodically “heartbeats” to the registry. Clients query the registry once per request (or cache responses) to obtain the current set of healthy instances. This is a *distributed consensus* problem reduced to a simple publish/subscribe model: the registry publishes state; clients subscribe to it.

Why must heartbeats exist? They provide an implicit **probabilistic guarantee** that a service is alive—if heartbeats stop, the registry assumes failure with high probability and removes the instance. This turns a deterministic availability problem into one governed by *Markovian* failure models, allowing scalable fault tolerance without complex leader election.

A non‑obvious insight: **Eureka’s “soft‑naming” (service name + version)** is not just convenience—it enforces *semantic versioning* of APIs. Clients can bind to a particular version and receive a graceful fallback if the newer one fails, effectively turning runtime dependency management into an explicit optimization objective.

In sum, Eureka transforms dynamic service discovery from a brittle configuration problem into a lightweight, probabilistic, and optimizable system that scales with the cloud’s elasticity.
