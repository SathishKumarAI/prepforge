**Typical pattern in ML libraries**

- **Core hyperparameters** that are *mandatory* and *highly coupled* (e.g., `n_estimators`, `max_depth` for trees) → positional.
- **Optional tuning knobs** (`min_samples_split=2`, `random_state=None`) → keyword, often with defaults.

This design balances performance and usability: the critical path stays tight, while flexibility is preserved where it matters most.

## Edge Cases  

- **Large APIs** (e.g., `torch.nn.Module.__init__` with dozens of flags) become unwieldy if all are positional.  
- **Backward compatibility**: Adding a new positional arg can break downstream code; keyword args mitigate this.  
- **Type checking tools** may flag missing arguments differently for positional vs. keyword.

## Optimize & Communicate  

To improve, libraries adopt *mixed signatures*: mandatory hyperparameters positional, optional ones keyword with defaults. For public APIs, document the order clearly and provide autogenerated docs (Sphinx/NumPy style). During a live interview, you’d emphasize that while positional args give speed and clarity for core functions, keyword arguments are essential for extensibility—exactly what large ML frameworks strike a balance between.
