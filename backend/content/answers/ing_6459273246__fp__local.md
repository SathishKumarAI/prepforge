**Cost comparison of vector databases**

The fundamental problem a vector database solves is *nearest‑neighbour search* over high‑dimensional embeddings. In an ideal world we would scan every vector (O(n) time) but that quickly becomes infeasible as n grows. The cost therefore splits into two orthogonal axes:

| Axis | What drives it | Why it matters |
|------|----------------|----------------|
| **Memory footprint** | Size of the raw vectors + any index structures | RAM is expensive; disk‑based indices add I/O latency |
| **Query throughput** | Indexing strategy (flat, IVF, HNSW, PQ) + hardware acceleration | More sophisticated indexes reduce search time but increase construction/maintenance overhead |

From an information‑theoretic standpoint, the *entropy* of the dataset determines how many partitions or clusters are needed for a given recall. If embeddings lie on a low‑dimensional manifold, we can compress them aggressively (product quantization) without losing much distance fidelity, drastically cutting both memory and CPU cost.

**Non‑obvious insight:**  
The *index update cost* is often the hidden killer. A naïve IVF index rebuilds all centroids every time new data arrives—O(n log k). Modern systems amortize this by maintaining a *lazy‑update buffer* that only re‑clusters after a threshold of inserts, keeping query latency stable while still honoring freshness constraints.

In practice, the optimal trade‑off is found by treating cost as a function  
\(C = \alpha M + \beta Q\) where \(M\) is memory, \(Q\) query time, and \(\alpha,\beta\) capture vendor pricing. By profiling *entropy* and *update frequency*, you can solve for the minimal \(C\) that satisfies your service level agreements—rather than blindly picking a “fastest” index.
