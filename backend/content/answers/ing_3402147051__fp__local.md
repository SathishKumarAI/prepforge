**Load balancing in machine‑learning systems**

At its core, a learning system must map *inputs* (features) to *outputs* (predictions) fast enough that users perceive real‑time performance. The fundamental problem is that each inference call consumes CPU/GPU cycles, memory bandwidth and sometimes specialized accelerators. If every request is sent to a single model instance, the service saturates once its per‑second throughput limit is reached—latency spikes, errors rise, and scaling becomes expensive.

A load balancer solves this by **optimizing resource utilization under stochastic demand**. It treats inference requests as jobs in a queuing system and distributes them across *k* identical or heterogeneous workers so that the *expected response time* \(E[T]\) is minimized while keeping all queues stable. Mathematically, for homogeneous workers with service rate \(\mu\), assigning \(n_i\) requests to worker \(i\) yields

\[
E[T] = \frac{1}{k}\sum_{i=1}^{k} \frac{1}{\mu - n_i/\text{slot}}
\]

where “slot” is the number of concurrent threads per worker. The optimal policy, derived from queue‑theoretic principles (e.g., M/M/1 queues), is to keep all workers at roughly equal load: \(n_1 \approx n_2 \approx \dots \approx n_k\).

**Non‑obvious insight:**  
Most designs focus on *throughput* and ignore **cold‑start latency** of model weights. In a dynamic environment (e.g., auto‑scaling or multi‑model serving), the load balancer should also monitor *weight‑loading time* and pre‑warm under‑utilized workers before routing traffic, thereby reducing variance in response times even when overall load is low.

In practice, this translates to health checks, weighted round‑robin or least‑concurrent algorithms, and adaptive scaling loops that treat inference latency as a first‑class metric rather than an afterthought.
