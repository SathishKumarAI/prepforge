**Why benchmarking must be an *objective* measurement**

At its core a benchmark is a statistical test: it asks “given two systems, how often does one predict the correct answer?” The only thing that can change this probability is **the data distribution** and **the evaluation protocol**. If either is tainted—by leaking training samples, by cherry‑picking cases, or by allowing extra compute during inference—the resulting accuracy no longer reflects true generalisation.

**Key principles to guard against contamination**

| Principle | Implementation |
|-----------|----------------|
| *Data isolation* | Maintain a strictly separate hold‑out set that never appears in pre‑training, fine‑tuning, or any hyper‑parameter sweep. Use a hash‑based split and store the seed publicly. |
| *Protocol reproducibility* | Fix tokenisation, padding, beam width, temperature, etc., and publish the exact script (including random seeds). Run it on a clean, read‑only environment (e.g., Docker image with no internet access). |
| *Audit trail* | Log every inference call: timestamp, model version, hardware ID. Store logs in an append‑only ledger that cannot be edited post‑facto. |
| *Independent validation* | Invite external parties to run the same script on their own hardware and compare results within a tight variance margin. |

**A non‑obvious insight**

Even with perfect isolation, **hardware variability** can bias scores: GPUs with larger cache or faster memory may finish more beam steps before truncation, subtly inflating perplexity. Normalising by *effective compute* (e.g., FLOPs per token) or reporting *latency‑per‑token* alongside accuracy mitigates this hidden source of contamination.

By treating benchmarking as a *controlled experiment* governed by data isolation, protocol reproducibility, auditability, and hardware normalisation, you ensure that the numbers truly reflect model quality rather than artefacts.
