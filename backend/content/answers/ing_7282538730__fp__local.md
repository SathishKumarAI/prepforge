**Why mix them?**  
At the core, a client needs *data*; the server must *expose* that data efficiently and safely. REST is a *resource‑oriented* protocol: each URL maps to a fixed shape of JSON, and CRUD operations are baked into HTTP verbs. GraphQL, by contrast, is a *query language* that lets the client request exactly what it wants in one round trip, with no over‑fetching or under‑fetching.

When you add a new domain (e.g., “orders” vs “inventory”), you can keep the existing REST endpoints for legacy consumers and expose a GraphQL schema that aggregates those resources plus new ones. The two layers are orthogonal: REST handles **state mutation** and **security** (fine‑grained RBAC on URLs), while GraphQL manages **introspection, pagination, and batched reads**.

**Non‑obvious insight:**  
GraphQL’s *type system* is not just a contract; it can act as an incremental API migration tool. By adding new fields to the schema without breaking existing ones, you can evolve your data model while keeping REST endpoints untouched. The server can even proxy GraphQL queries through REST adapters internally—so the same business logic serves both interfaces.

In short: use REST for stable, versioned write operations and legacy clients; deploy GraphQL for flexible, read‑heavy scenarios where consumers benefit from precise shape control.
