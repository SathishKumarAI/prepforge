**Why GraphQL’s “single point of entry” is essential**

The core problem in web APIs is *data coupling*: a client must know which endpoint returns the fields it needs and how many round‑trips to make. REST solves this by exposing many resource URLs, but each URL embodies a rigid shape of data. The client either requests everything (`/users`) or nothing; if it wants a subset it still receives the whole payload, wasting bandwidth.

GraphQL reframes the problem as *information retrieval*: the client asks **what** it needs, and the server supplies exactly that set. By exposing one endpoint (`POST /graphql`), the protocol removes the surface‑area of routing logic: every request is parsed into a query tree whose shape encodes the required fields. The server then walks this tree once, fetching only the necessary data, regardless of how many logical resources are involved.

This design rests on two deeper principles:

1. **Optimization by declarative intent** – the client’s intent (a tree of fields) is a concise specification; the server optimizes data fetching accordingly.
2. **Uniform interface abstraction** – treating every query as a single, composable request eliminates versioning and endpoint proliferation.

A non‑obvious insight: the “single point” is not a performance trick but an *information‑theoretic guarantee*: the client’s bandwidth cost equals the size of the requested subgraph, never larger. Thus GraphQL turns the API surface into a zero‑overhead contract between intent and delivery.
