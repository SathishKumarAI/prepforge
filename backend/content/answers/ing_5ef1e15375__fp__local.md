**Why the JVM must “unwind” a call stack**

When a method throws an exception it signals that its contract was violated.  
The JVM’s fundamental responsibility is to restore *program state* to a place
where the exception can be handled or, if none exists, terminate the thread.
This requires two operations:

1. **Unwinding** – walking up the stack frames, discarding local variables and
   restoring saved registers until a frame declares a handler for that
   exception type.
2. **Dispatching** – once a suitable handler is found, control jumps to its
   bytecode, with the exception object stored in a hidden slot.

The JVM implements this via the *exception table* generated by the compiler:
for each bytecode range it records `start_pc`, `end_pc`, `handler_pc`,
and the `catch_type`.  
When an exception is thrown (via `ATHROW`), the interpreter or JIT
runtime:

- captures the exception object,
- starts at the current frame’s program counter, and
- iteratively checks each ancestor frame’s exception table for a matching type.
  If none matches, it propagates to the thread’s uncaught‑exception handler.

**Non‑obvious insight**

The *search order* is not “closest match first” but **lexical order of catch blocks**.  
If two `catch` clauses can handle the same exception (e.g., a superclass and
a subclass), the JVM will choose the one that appears first in source order,
not necessarily the most specific type.  This subtlety can lead to surprising
behaviour when refactoring exception hierarchies, underscoring why developers
should prefer explicit catch blocks over generic ones.
