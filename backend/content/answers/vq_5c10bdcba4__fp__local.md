**Implicit Parameter – first‑principles view**

In data pipelines we often need the same context (e.g., a `SparkSession`, a catalog, or a schema registry) in many functions, yet passing it explicitly bloats signatures and forces callers to remember the order of arguments.  
The *implicit parameter* mechanism solves this by treating a value as **contextual metadata** that can be automatically supplied by the compiler when a function is invoked. It is grounded in *type‑class* inference: the compiler searches the current scope for an instance matching the required type and injects it, just as it would resolve a generic type parameter.

Why this works:
1. **Separation of concerns** – business logic stays pure; plumbing lives elsewhere.
2. **Compile‑time safety** – if no implicit is found, compilation fails, preventing silent misconfigurations.
3. **Extensibility** – new contexts can be added without touching existing APIs; they are discovered automatically.

A non‑obvious insight: *implicit parameters perform dependency injection at the type level*, enabling modularity without runtime reflection or service locators. They preserve zero runtime overhead because the resolution happens during compilation, yielding ordinary function calls in the generated bytecode. This blend of compile‑time guarantees and runtime efficiency is what makes implicit parameters uniquely powerful for data engineering workflows.
