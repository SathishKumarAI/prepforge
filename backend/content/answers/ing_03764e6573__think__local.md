**1️⃣ Clarify the goal & audience**  
- *What is the end‑product?* (e.g., a demo model, a research proposal, an architecture diagram).  
- *Who will use it?* (students, stakeholders, peers) – this shapes the level of detail and jargon.  

**2️⃣ Define the scope & constraints**  
- *Which AI subfield?* (ML, NLP, CV, RL).  
- *What data or resources are available?* (public datasets, compute limits).  
- *Any time or budget limits?* This determines how deep you can go.

**3️⃣ Unpack assumptions & pre‑knowledge**  
- *Do participants know the basics of ML pipelines?*  
- *Are there domain‑specific terms they’ll need clarified?*  

**4️⃣ Elicit pain points and success criteria**  
- *What problems should the solution solve?* (accuracy, fairness, latency).  
- *How will we measure “success”?* (metrics, user stories).

**5️⃣ Plan for iterative feedback**  
- *When will you pause to review progress?*  
- *Who can provide quick sanity checks?*

### How to apply this in a whiteboard session

1. **Start with the goal & audience** – write it on the board.  
2. **Sketch the high‑level architecture** while labeling constraints (data, compute).  
3. **List assumptions** next to each component.  
4. **Map pain points → design choices** and note success metrics.  
5. **Iterate**: stop after each block, ask “Did we cover this assumption?” or “Does this metric align with the goal?”

### Common traps

- Skipping scope definition → end up building a solution that nobody needs.  
- Assuming too much prior knowledge → participants get lost.  
- Over‑engineering early – keep it simple until constraints force complexity.

### Sanity check

Read back the board aloud:  
> “We’re building an NLP classifier for X, with Y data and Z compute, aiming for accuracy ≥ A%. We assume users know basic ML pipelines. Success is measured by metric M.”  

If any part feels vague or unsupported, ask a quick clarifying question before moving on.
