**Why we need an API for authentication**

At the core of every distributed service is *separation of concerns*: a user interface, business logic, and data storage should not be entangled. When one component (e.g., a mobile app) needs to verify a user’s identity, it must hand off that responsibility to a dedicated **Authentication Service**. The question becomes: how does the client talk to that service without exposing its internals? An **API (Application Programming Interface)** is the contract that solves this.

1. **Encapsulation + Interoperability**  
   The API defines a set of endpoints (`/login`, `/refresh`) and message formats (JSON, OAuth tokens). Clients can call these over HTTP regardless of language or platform; the service hides its database schema, hashing algorithms, and rate‑limiting logic behind that contract.

2. **Protocol‑agnostic Security**  
   By exposing only a stateless token exchange protocol, the API removes direct credential handling from clients, reducing attack surface. The server can rotate secrets, enforce MFA, or integrate with third‑party identity providers—all invisible to the caller.

3. **Scalable Composition**  
   In microservice architectures, many services need authenticated context. A single authentication API issues short‑lived bearer tokens that any downstream service can validate locally (e.g., via JWT), enabling horizontal scaling without repeated credential checks.

**Non‑obvious insight:**  
The *shape* of the API matters more than its security level. A poorly designed endpoint (e.g., overloading `/login` with user profile updates) forces clients to perform extra roundtrips or embed business logic, leading to tighter coupling and higher latency. Thus, a clean, minimal authentication API is itself an optimization problem: it reduces communication cost while preserving the separation of concerns that keeps the system maintainable.
