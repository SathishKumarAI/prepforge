**Event‑sourcing is like keeping a diary of every change that happens in a system, rather than just storing the final page.**

Imagine you run a library. Instead of writing down only the current list of books on the shelf, you keep a notebook where each line records *exactly what happened*: “Book A was added”, “Book B was checked out”, “Book C was returned”. Later, if you need to know how many copies of Book A were ever available or why a certain error occurred, you simply read the diary and replay all those entries in order. The current state of the library is then rebuilt by applying each recorded event sequentially.

In event‑driven architecture, every change is an **event** (a small, immutable record of something that happened). By storing all events—never just the end result—you get a complete history, audit trail, and the ability to reconstruct any past state. This is event‑sourcing: persisting only the sequence of events instead of snapshots of state.
