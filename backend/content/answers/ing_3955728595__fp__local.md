**GraphQL vs REST – why one is not a drop‑in replacement**

At its core, an API must *translate* client intent into server data while keeping the interface stable.  
REST does this by exposing fixed endpoints; each endpoint returns a pre‑defined shape of JSON. The *problem* it solves is “how to fetch related resources without over‑ or under‑fetching.” REST answers with **hypermedia** (links) and **pagination**, but the client must still issue multiple round‑trips or accept bloated payloads.

GraphQL reframes the problem: treat the query itself as a *declarative contract*. The client sends a tree that mirrors exactly what it needs; the server responds with a matching shape. This shifts the burden from designing endpoints to enforcing **type safety** and **schema introspection**. The deeper principle is *information minimization*: the query’s structure dictates the information flow, eliminating guesswork.

Non‑obvious insight: because GraphQL queries are first‑class citizens, they become **caches of intent**. A single endpoint can be reused for many use‑cases, yet each client still benefits from fine‑grained caching (e.g., by query hash). Thus, while GraphQL is not a literal REST replacement, it offers an optimization layer that turns the API into a *query language*, enabling efficient data retrieval and evolution without breaking clients.
