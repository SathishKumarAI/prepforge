**Why production ML exists**

A model is only useful if it *keeps* delivering correct predictions in the real world.  
The core problem is that data streams change (concept drift), user behaviour shifts, and
inference latency must stay below a hard deadline.  Hence we must treat an ML pipeline as a **continuous optimisation loop**:  
1) gather fresh data → 2) retrain or update → 3) deploy with monitoring → 4) rollback if performance degrades.

This loop is governed by *information‑theoretic* constraints: the amount of new evidence that can be assimilated per unit time (bandwidth, compute) must match the entropy rate of the environment.  If the environment’s entropy exceeds our update capacity, predictions inevitably diverge.

**Deep principle**

The system is a **control‑system** over a stochastic process.  
- *State*: current model parameters θ.  
- *Observation*: streaming data xₜ with labels yₜ (often delayed).  
- *Action*: update rule Δθ = f(θ, xₜ, yₜ).  

Stability of this control loop is ensured by regularisation, learning‑rate decay, and A/B testing—exactly the same mechanisms that guarantee convergence in online convex optimisation.

**Non‑obvious insight**

Most people treat deployment as “push the model to production.”  
In reality, *deployment is a hypothesis test*: every inference batch becomes evidence for whether the deployed θ still maximises expected utility under current data distribution.  Therefore, continuous validation (confidence intervals on AUC, drift detectors) is not optional but a **statistical necessity**—otherwise you’re effectively performing a blind experiment with no guarantees of safety or fairness.

In short, production ML is a disciplined, statistically‑grounded control loop that keeps the model’s information flow in sync with the world’s entropy.
